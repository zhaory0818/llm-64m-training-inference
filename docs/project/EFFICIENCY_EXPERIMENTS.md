# 训练与推理效率改进：实现、对照与结果

2026-10-31，MiniMind Dense 63,912,192参数；RTX3060 Laptop 6GB；Torch2.6.0+cu124、Transformers4.57.6。实验使用自己的通用SFT及医疗LoRA，不购买云算力或调用付费API。

## 本次完成的工作

围绕固定补齐浪费、缓存解码算子路径和LoRA部署开销，增加可选的训练/推理实现，建立预先冻结协议、正确性检查、同负载计时及独立确认负载。实际执行270次推理计时、12组训练计时，共384次正式计时AdamW更新；另有预热、资源短测和入口验证。训练性能实验不保存新的质量模型，不覆盖原成果。

本机完整档案：`logs/resume_evidence/run_20261031_165419/`。轻量结果副本：`docs/project/evidence/efficiency/`，图：`docs/project/figures/efficiency/efficiency.png`。

## 1. 动态右侧补齐：有效吞吐提升约15%

原Dataset将每条样本补齐到768。新增`dataset/batch_collator.py`在DataLoader整理批次时，只移除整个batch共同不用的尾部PAD，并按8向上对齐。保留忽略监督的真实上下文、EOS、内部PAD及监督位置；不更改截断、标签右移、样本顺序或做packing。可附带真实长度元数据，避免把尾部真实PAD-ID误认成补齐；原SFT语料已逐行核验PAD均为非监督位置。

先从先前均匀抽样审计中确定1024条真实SFT样本，冻结原Dataset随机预处理后的输入和标签，分为两个512条候选池。各池实际计时使用同样128条独立样本，每次32更新、batch4、重复3次；每次前12条样本用于3次预热，预热后恢复初始化并清零Adam状态。并非完整训练1024条，也没有扩大SFT语料。两个池的计时样本不重叠。

固定FP32参数、BF16 autocast、AdamW lr=1e-5、clip1、accumulation1、workers0；只改变批次尾部PAD。计时包含整理、传输和训练，GPU事件另记计算段。

为隔离随机预处理与计算形状，计时使用预先token化的冻结Tensor数据，不包括完整JSONL加载、Arrow缓存构建或在线分词；实际全数据训练的端到端收益可能更小。不能把本微基准直接换算为历史云端账单节省。

| 指标 | 开发负载：固定 → 动态 | 确认负载：固定 → 动态 |
|---|---:|---:|
| 每次32更新的有效输入token | 60,326 → 60,326 | 64,034 → 64,034 |
| 有效监督目标token | 49,570 → 49,570 | 52,982 → 52,982 |
| 实际处理位置 | 98,304 → 81,984 | 98,304 → 82,272 |
| 平均批次长度 | 768 → 640.5 | 768 → 642.75 |
| PAD比例 | 38.63% → 26.42% | 34.86% → 22.17% |
| 有效输入token/s，中位数 | 13,149 → 15,173 | 13,666 → 15,924 |
| 毫秒/更新，各侧中位数 | 143.37 → 124.25 | 146.42 → 125.67 |
| **配对吞吐比的中位提升** | **15.39%** | **15.25%** |
| 各配对吞吐提升范围 | 14.67%～15.49% | 13.34%～16.63% |
| 峰值allocated，GiB | 2.345 → 2.339 | 2.345 → 2.341 |

配对比中位数与“两侧各自中位数相除”是不同统计量，因此最后百分比不能直接从上方两列中位数反推。按配对比折算的耗时下降为13.34%和13.24%，不能把吞吐增长15%写成时间下降15%。

峰值显存几乎不变：部分batch仍达768，模型/梯度/优化器占用也不因裁PAD消失。动态shape下reserved反而略增：开发2.574→2.699GiB、确认2.574→2.660GiB。**本项适合写减少无效计算与吞吐提升，不写大幅节省显存**。batch16时batch最大长度可能更长，本机batch4结果不能直接推广。

正确性：所有1024条样本的有效前缀与监督计数保持；小批次FP32 loss差4.77e-7、梯度相对L2误差2.53e-6；实际BF16 loss差1.86e-4、梯度相对L2误差1.84%。后者来自形状变化影响浮点计算，符合预设阈值，但不意味着长期训练轨迹逐位一致。12组均检查Adam步数、有限loss/梯度/参数和非零参数变化。

实际SFT入口新增`--dynamic_padding 1 --pad_to_multiple 8`，默认0保留原行为；本轮未重训完整SFT。

## 2. 定位缓存解码瓶颈并新增SDPA路径

初次90组缓存/投影计时中，某些短序列下关闭KV cache反而更快。代码检查发现：原Attention只在多token且无past时进入SDPA，缓存单token解码仍执行手写矩阵乘、FP32 softmax和矩阵乘。KV cache节省重复计算，并不保证这份小模型实现的kernel调度一定更快。

新增`model/inference_optimizations.py`：仅在eval、use_cache、已有past、单query且无实际掩码时使用SDPA；原RoPE、q/k norm、GQA和KV结构不变。此时所有key都是过去和当前位置，应使用`is_causal=False`；套用单query的左上角causal mask会错误地只看第一个key。训练、prefill、多token续写和实际padding掩码回退原实现。全1掩码在generate入口归一化一次，避免逐层检查。

Profiler验证，8层缓存解码由16次bmm、8次softmax，切换为8次SDPA。当前GPU实际选到`_scaled_dot_product_efficient_attention`，**不把它写成自己实现了FlashAttention或自定义CUDA kernel**。

这是初次结果提出的追加假设，已单独登记协议后再测：3种输入长度32/128/512、2种输出长度32/128、4种配置、重复5次共120次；另用不同文本、256输入+64输出确认20次。固定batch1、FP16、greedy、禁EOS早停、相同生成次数，随机化顺序并预热、CUDA同步。计时是模型级forward生成循环，**不是HTTP TTFT或并发服务吞吐**。

| 相对原默认cache开启、全位置投影 | 开发30配对：吞吐比中位提升 | 确认5配对：吞吐比中位提升 |
|---|---:|---:|
| 仅末位置投影 | -2.44% | -7.78% |
| 仅缓存SDPA | +13.24% | +8.57% |
| **缓存SDPA＋末位置投影** | **+13.88%** | **+10.97%** |

每个cell的原始数值、min/max均保留；确认组合的单对比值范围0.985～1.352，Windows笔记本负载和频率造成明显波动。结论是测试矩阵与确认负载的中位收益，不是所有输入都加速的保证，也不取最快一次当成绩。

这是交互式Windows桌面上的实验，最终资源检查还可见其他应用的GPU上下文；本轮没有关闭用户应用或排他占用整卡。不能据此确定某次波动的具体原因，也不把结果包装为实验室稳态或生产服务SLA。

末位置投影复用了原forward的`logits_to_keep`接口，主要减少prefill词表投影；缓存decode本来就只含一个位置。单独开启没有稳定整体加速，保留为可选项，不作为单独正收益卖点。

FP32/FP16在32/128/512长度、每组17个相同teacher-forced位置检查logits，FP32最大绝对差1.43e-5；FP16最大0.02734、相对L2最高0.000969；所测argmax均相同。实际padding掩码回退生成一致。全部35组开发/确认生成负载中，三种候选的greedy结果都与原路径一致；这不等于对所有输入或随机采样输出的普遍等价证明。

## 3. LoRA合并部署对照

同一SFT+医疗适配器，对照运行时LoRA分支与已保存合并模型；不改任务、batch、精度、cache和输出预算。开发10配对吞吐中位提升10.35%，另一组确认5配对提升14.37%。开发单对范围-15.29%～+15.50%，确认+10.24%～+19.85%，保留波动，不把合并公式称原创。

3组长度的FP16 logit平均绝对误差最高0.00204，32token greedy均一致。393,216个LoRA参数约占基座0.615%；适配器797,242字节，约为基座权重文件0.579%。合并模型仍需完整权重约137.7MB，不能说“合并后模型缩小99%”。

## 5. 面试应能解释的三个问题

1. **为什么裁PAD不改变监督，却可能改变浮点值？** Decoder因果注意力中前缀不看尾部；但矩阵shape改变会影响kernel选择和浮点累加。用有效logit、loss、梯度及真实更新分别检查。
2. **为什么有cache仍可能慢？** 缓存减少理论运算，但小模型受kernel调度、低效softmax、内存访问和CPU发射影响；先测量，再用profiler确认路径。
3. **如何证明加速不是少训练/少生成？** 两侧固定输入、监督token、更新次数、初始化、精度和输出步数；预热排除，随机/交替顺序，独立确认负载，并保存全部原始记录。

这三项与既有从零训练、医疗适配、偏好优化、短程RL和服务链路一起，构成简历素材；不需要把效率结果改写为不存在的准确率提升。
